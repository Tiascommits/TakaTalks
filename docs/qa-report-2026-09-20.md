**Security review of `fcd8c23`.** One identification pass found four candidates; each was
then re-checked independently against the false-positive rules. Nothing reached the
report threshold (confidence ≥ 8):

- *Phone-OTP attempt limiter keyed on the guess* — a genuine logic bug (limiter never
  throttles), but **dormant**: no phone token can exist until the `WHATSAPP_*` variables
  are configured. **Fixed properly**: each guess now spends one of the pending token's
  attempts in a single atomic `UPDATE ... WHERE attempts < 5` *before* it is compared,
  stored in the database (new `VerificationToken.attempts` column, migration
  `20260920120000_add_verification_attempts`) so it holds across serverless instances. A
  60-second resend cooldown per phone stops "request a fresh code, spend its guesses,
  repeat" from resetting the budget. Real-database e2e tests include a 30-way concurrent
  burst that must evaluate exactly 5 guesses (it does: 5 evaluated, 25 blocked).
- Three hardening notes, rated not exploitable in this deployment — **all fixed**:
  - *Session secret*: no baked-in default; in production, with neither `SESSION_SECRET`
    nor `ADMIN_SECRET` set, signing now throws. `SESSION_SECRET` is documented in
    `.env.example`.
  - *SSRF guard*: replaced by `src/lib/net/safe-fetch.ts` — strict IPv4/IPv6 range checks
    (bracketed and IPv4-mapped IPv6, `0.0.0.0`, `127/8`, CGNAT, link-local…), DNS
    resolution with every address checked, manual redirects re-validated per hop, and a
    streamed size cap. One documented limit remains: DNS rebinding between check and
    connect (needs a pinned-IP dispatcher).
  - *Magic link not bound to the browser*: a cookie binding would break "request on the
    laptop, open the email on the phone", so the confirmation screen instead shows the
    **masked** email the link signs in ("a•••@example.com") and tells the user to stop if
    it isn't theirs. The preview endpoint answers for email links only, so it can't be a
    guess-checking oracle for OTPs.
- *Found by the review pass, outside this diff:* `/api/admin/setup` compared
  `secret !== process.env.ADMIN_SECRET`, so with `ADMIN_SECRET` unset an omitted secret
  compared equal. **Fixed**: it refuses (503) when the secret isn't configured and
  compares in constant time.

**Deployment notes** for the next release:
- `vercel-build` runs `prisma migrate deploy`, which will apply the new migration; it is a
  plain `ADD COLUMN ... DEFAULT 0`, so existing rows are fine.
- Production must have `SESSION_SECRET` **or** `ADMIN_SECRET` set (`ADMIN_SECRET` is
  already required for the admin pages). If neither is set, tracker reads/writes that touch
  the session cookie now fail loudly instead of silently using a public default. Check the
  Vercel environment before deploying.

## The 3 e2e failures (first pass — all since fixed, see Revision 2)

At the time of the first pass the suite was **not green**. I traced each failure to its cause with the failing trace
context plus a separate scratch Playwright script against a production server. None is a
product breakage, but all three are stale assertions that need a decision.

### 1. `calculator.spec.ts:58` — rebate optimizer appears with a suggestion

`getByText("রিবেট অপটিমাইজার")` hit a strict-mode violation: it now matches **two**
elements. `CalculatorHeader.tsx` was rewritten in this batch and its intro paragraph now
contains the phrase "রিবেট অপটিমাইজার" as well as the optimizer's `<h2>`.

The feature itself works. Probed after entering ৳50,00,000 business profit: the optimizer
heading is visible and the "বাঁচাতে পারো" savings text is visible, with no NaN/Infinity/
undefined. **Cause: test locator made ambiguous by the header copy change.** Fix: locate the
heading by role (`getByRole("heading", { name: "রিবেট অপটিমাইজার" })`).

### 2. `tracker.spec.ts:157` — accepts an extremely large investment

The test enters a principal of ৳999,999,999,999 and expects it to be saved. This batch adds
an upper bound to `POST /api/investments` (`principalAmount <= 100_000_000_000`, i.e. ৳100
billion), so the request is rejected with 400.

Boundary probed against the running app: ৳99,999,999,999 accepted, ৳100,000,000,000
accepted, ৳100,000,000,001 rejected, ৳999,999,999,999 rejected. The cap behaves exactly as
coded. **Cause: intentional hardening, test not updated.** The test should be changed to
expect either an accepted value under the cap or a rejection above it.

Related UX finding (low severity): the rejection shows the generic "সেভ করা যায়নি, আবার
চেষ্টা করো।" ("Couldn't save, try again"). Retrying can never succeed for an over-cap
amount, and the zero/negative-amount cases get a specific inline error. Consider a
client-side check with a specific message.

### 3. `videos.spec.ts:25` — homepage reel links through to /videos

The test looks for a link named `/See all videos|সব ভিডিও দেখুন/`. The homepage's actual
links read `SEE ALL VIDEOS →` (case differs) and `সব ভিডিও →` (no "দেখুন"), so the locator
can never match. That copy comes from `0703a29`, which is already on `main`, so this is
**pre-existing**, not from this batch. It was hidden until now: the last QA pass failed
earlier in the same test on the Facebook-iframe assertion, which this batch's
`videos.spec.ts` change relaxed to `video, iframe`.

The behaviour is fine: probed by clicking the homepage "সব ভিডিও →" link, which navigates to
`/videos`, and the reel does render a `<video>` element. Fix: update the locator's regex.

For comparison, the last report's 2 failures were both video-iframe assertions; this run has
1 video failure (a different cause) plus 2 new ones from this batch.
